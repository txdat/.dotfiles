# /run-stack — Drive a Stack to Publication

Take a stack ([plan.md — Stacks](plan.md#stacks)), or one plan, through review-feature, execute-feature, and review-code, and stop where the user decides. Pass the root, then optionally `--until`. [dev-stack.sh](../../bin/dev-stack.sh) `next <root>` prints each plan's next action; a phase it names runnable has passed its gate. If `next` fails, report its error and stop.

`--until review-feature|execute-feature|review-code` (default `review-code`) caps the phases started; revise is review-feature. A runnable phase past the cap is held: not started, never recorded as stopped. Under `execute-feature`, a child still waits for its parent to be `reviewed`. An unknown or repeated option, or an invalid value, is reported before step 1, and nothing starts.

1. Run `dev-stack.sh next <root>`.
2. Start every runnable plan except create-pr and held phases, each in its own subagent. This session is the main agent for every plan:
   - **review-feature:** a fresh reviewer on the model [README](../../README.md#references) gives the review skill, set up under [plan.md — Review](plan.md#review), with the paths of the plans below it. Record its verdict with `dev-stack.sh review <plan> ready|needs-changes`. A re-review also gets the prior findings and what changed.
   - **revise:** a subagent given the review's findings revises the plan under [design-feature.md — Revise](design-feature.md#7-revise-after-review), leaving its re-review to review-feature, which `next` then names. If the findings are lost, run review-feature again to get them. A finding that needs a decision stops the plan.
   - **execute-feature:** a subagent invokes the skill `dev-execute-feature <plan>` and returns without starting review-code.
   - **review-code:** a fresh reviewer as for review-feature. On a pass, finalize under [review-code.md — Finalize](review-code.md#finalize); otherwise repair in the plan's worktree and re-review.
   Without subagents, run them one at a time here, reviewing directly and saying so. Start each by reading its phase skill, `skills/dev/<phase>.md`, again with the file-read tool, never a shell command, in the same message that says `Starting <phase> on <plan path>` and names no other plan, so a gate that reads the plan from that message checks it.
3. As each subagent returns, finish its step, rerun `next`, and start what became runnable. Never poll; the run ends when nothing is running and step 2 has nothing to start.
4. Report the tree from `dev-stack.sh next <root> --tree` in a text block, or the table from `--md` when the user asks for one, then group the plans as: for the user (approvals, revisions that need a decision, stopped plans with their reasons, and create-pr when the stack is ready to publish), held by `--until` with the phase it would run, blocked with the reason, waiting on a parent, and done.

A plan stops when its review hits plan.md — Review's round limit, its fixes hit the three-attempt limit, its work stops under [plan.md — Changes](plan.md#changes), or a phase started on it returns without changing its next action. Record it at once with `dev-stack.sh stop <plan> "<reason>"`, including any `Failed fixes: <n>/3`; the record goes to the stack's `stops.log`, not the plan; `next` then shows it `stopped` until its status (a review verdict does not count), its spec or a spec below it, or its Branch's tip changes, or the user clears it with `dev-stack.sh resume <plan>`; reverting the change restores the stop. A stop citing `Failed fixes: 3/3` or more holds, through later stops too, until resume, the user granting more attempts. Only the user runs `resume`. The rest of the stack continues. Never set `Status: approved` or run create-pr; the user does.
