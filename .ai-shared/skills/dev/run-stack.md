# /run-stack — Drive a Stack to Publication

Take a stack ([plan.md — Stacks](plan.md#stacks)), or one plan, through review-feature, execute-feature, review-code, and create-pr, and stop where the user decides. Pass the root, then optionally `--until` and `--auto-approve`. [dev-stack.sh](../../bin/dev-stack.sh) `next <root>` prints each plan's next action; a phase it names runnable has passed its gate. If `next` fails, report its error and stop.

`--until review-feature|execute-feature|review-code|create-pr` (default `create-pr`) caps the phases started; revise is review-feature. The user invoking or asking for run-stack without a lower cap authorizes create-pr's pushes and pull requests, draft unless the user asks for ready; `--until review-code` stops before publication. `--auto-approve`, passed only by [autopilot](autopilot.md), approves for the user: at each `wait-user`, run `dev-stack.sh approve <plan>` and rerun `next`; if `approve` fails, record its error as the plan's stop. A runnable phase past the cap is held: not started, never recorded as stopped. Under `execute-feature`, a child still waits for its parent to be `reviewed`. An unknown or repeated option, or an invalid value, is reported before step 1, and nothing starts.

1. Run `dev-stack.sh next <root>`.
2. Start every runnable phase that is not held, each in its own subagent except create-pr; where a named agent is not installed, the general-purpose agent gets its md file as its instructions. This session is the main agent for every plan:
   - **review-feature:** a fresh reviewer set up under [plan.md — Review](plan.md#review), with the paths of the plans below it. Record its verdict with `dev-stack.sh review <plan> ready|needs-changes`. A re-review also gets the prior findings and what changed.
   - **revise:** a subagent, [dev-planner](../../agents/dev-planner.md) where installed, on design-feature's [README](../../README.md#skills) model and effort, given the review's or stop's findings and the user's answers labeled as the user's, and under `--auto-approve` dev-autopilot's labeled as its own, revises the plan under [design-feature.md — Revise](design-feature.md#7-revise-after-review), leaving its re-review to review-feature, which `next` then names. If the findings are lost, run review-feature again to get them. A finding that needs a decision stops the plan; under `--auto-approve`, [autopilot.md — Decisions](autopilot.md#decisions) takes it unless that section stops it.
   - **execute-feature:** a subagent, [dev-executor](../../agents/dev-executor.md) where installed, on the skill's [README](../../README.md#skills) model and effort, invokes the skill `dev-execute-feature <plan>`, with its Branch commits delegated, and returns without starting review-code. This session first sets up the plan's worktree under [execute-feature.md](execute-feature.md) step 1, so the subagent resumes in it.
   - **review-code:** a fresh reviewer as for review-feature, with plan.md — Review's review-code inputs. On a pass, end the round under [plan.md — Review](plan.md#review) and finalize under [review-code.md — Finalize](review-code.md#finalize); otherwise rerun the findings and end the round under plan.md — Review, repair in the plan's worktree, and re-review. Code repairs go to a dev-executor chunk, with the files they touch and Branch commits delegated; a repair to the plan's tests stays here.
   - **create-pr:** `next` names it on the root once every plan is `reviewed`. Invoke the skill `dev-create-pr <root>` in a message that says `Starting create-pr on <root path>` and names no other plan, so its gate checks the root, and follow [create-pr.md](create-pr.md) through cleanup. CI follows [CORE.md — Work](../../CORE.md#work): never poll it; cite known results or report it unverified.
   Without subagents, run the other phases one at a time here, reviewing directly and saying so. Start each by reading its phase skill, `skills/dev/<phase>.md`, again with the file-read tool, never a shell command, in the same message that says `Starting <phase> on <plan path>` and names no other plan, so a gate that reads the plan from that message checks it.
3. As each subagent returns, finish its step, rerun `next`, and start what became runnable. Never poll; the run ends when nothing is running and step 2 has nothing to start.
4. Report the tree from `dev-stack.sh next <root> --tree` in a text block, or the table from `--md` when the user asks for one, then group the plans as: for the user (approvals, revisions that need a decision, and stopped plans with their reasons), held by `--until` with the phase it would run, blocked with the reason, waiting on a parent, and done. After create-pr, also list each PR's URL, draft or ready; under `--auto-approve`, each auto-approved plan.

A plan stops when its review hits plan.md — Review's round limit, its fixes hit the three-attempt limit, its work stops under [plan.md — Changes](plan.md#changes), or a phase started on it returns without changing its next action. Record it at once with `dev-stack.sh stop <plan> "<reason>"`, including any `Failed fixes: <n>/3`; the record goes to the stack's `stops.log`, not the plan; `next` then shows it `stopped` until its status (a review verdict does not count), its spec or a spec below it, or its Branch's tip changes, or the user clears it with `dev-stack.sh resume <plan>`; reverting the change restores the stop. A stop citing `Failed fixes: 3/3` or more holds, through later stops too, until resume, the user granting more attempts. Only the user runs `resume`. The rest of the stack continues. Never set `Status: approved`; the user does.
