# /autopilot — Requirement to Reviewed Draft PRs

Take one issue or requirement through triage, delivery, draft PRs, and one `/code-review` round. Pass the issue or requirement, then optionally `--until create-pr` to skip step 3, or, after a stop, its handoff path and the user's answers ([Resume](#resume)); any other option or value is reported before triage, and nothing starts. Invoking it authorizes the issue it creates, pushes without force, draft PRs, and `auto-approved` plans; never set `Status: approved`, which is the user's.

This session is the main agent: it routes, decides under [Decisions](#decisions), and runs run-stack, create-issue, create-pr, and every worktree, push, PR, and merge-forward itself; subagents commit only where a step delegates it, and create only the scratch worktrees their own skills make. `Status:` changes stay with the phase that owns them under [plan.md — Sequence](plan.md#sequence). Every other step runs in a subagent built from its row in [Handoffs](#handoffs), fresh except that one dev-planner serves the stack's design-feature and every revise step after it, and reviewers are kept under [plan.md — Review](plan.md#review); where an agent is not installed, the general-purpose agent gets that agent's md file as its instructions and the same row. Without subagents, run each step here, one at a time, and say so.

## Handoffs

Each prompt names the agent's job, gives [CODING.md](../../CODING.md), the row's inputs, delegated and off-limits actions, and expected return, says others share the codebase, and carries any `Failed fixes: <n>/3`; the subagent runs on the [README](../../README.md#skills) model and effort of the row's skill. A missing input is supplied before the subagent starts, never guessed; one no source has stops for the user. run-stack's phases take the inputs its step 2 and [plan.md — Review](plan.md#review) list.

## 1. Triage

1. **Input.** Read an issue (`#N` or URL) with `gh issue view`; anything else is the requirement as written.
2. **Bug or feature.** A bug is existing behavior that departs from expected, documented, or earlier behavior; anything else, or a request that reads either way, is a feature.
3. **Bug.** Run fix-bug. Stop if the bug does not reproduce, its mechanism stays unsupported, or its first fix option is containment or live-state remediation; otherwise take that option.
4. **Route.** Plan-backed unless one of these sends it to a direct edit: [plan.md — Scope](plan.md#scope); for a bug, fix-bug's route; for a feature, a change that stays in one module, the project's package, service, or top-level source directory, and changes no contract, data model, dependency, or rollout behavior. A change estimated at more than 3 files or 200 lines, tests excluded, is plan-backed unless plan.md — Scope requires a direct edit.
5. **Issue.** Without an input issue, run create-issue with the requirement, or for a bug with the problem, expected outcome, and diagnosis evidence, and in either case a `Triage` section giving the type and route with a one-line reason for each; use its `#N` from here on. With an input issue, give that section in the report.

## 2. Deliver

**Plan-backed.** Run design-feature with the requirement, the issue, and for a bug `Type: fix` with the proposal and its regression patch. Answer the questions it returns under [Decisions](#decisions), labeled as dev-autopilot's, and resume it until it returns the stack; keep it for run-stack's revise steps. Run [run-stack](run-stack.md) `<root> --auto-approve`, which publishes the stack as draft PRs and cleans up once every plan is `reviewed`. When it ends with a plan stopped under [plan.md — Changes](plan.md#changes), apply [Decisions](#decisions); step 4's stop applies only when Decisions stops.

**Direct edit.** On Base, the default branch unless the issue names one, create a worktree with [dev-worktree.sh](../../bin/dev-worktree.sh) `create <issue>_<slug> <branch> origin/<Base>`, the branch named by the project's convention, and run `link-deps <worktree>`. Delegate the change with its exclusive files and commits on that branch. A code change starts with a failing test (for a bug, from the regression patch), shown failing and committed, then the change, shown passing; a docs or declarative config change, such as this dev flow's skills ([plan.md — Scope](plan.md#scope)), is the change alone. Either way, any original reproduction is rerun and the project's local checks pass. After the chunk returns, the main agent runs any review the project's instructions require, reruns the checks, and, for a code change, confirms the test commit fails without the change; a failure returns to the chunk as a fix attempt. Then push with `git push -u origin <branch>` and open `gh pr create --draft --base <Base>` with a body under [create-pr.md](create-pr.md)'s rules.

## 3. Review the PRs

This step runs outside the plan-backed workflow: the plans are published, so no plan, `Status:`, or gate applies, and fixes follow the findings, not the spec. Review every PR before fixing any. For each PR, parents first, run `/code-review <level> <PR number>` review-only, without `--fix` or `--comment`, where `<level>` is review-code's effort in the README; never `ultra`. Where `/code-review` is unavailable, review `gh pr diff <PR number>` for correctness and security under CODING.md, with each finding's location and evidence. Correctness and security findings block when they have a location and evidence; cleanups and findings without a location or evidence are reported, not applied.

Then fix the blocking findings, parents first. Fix each finding on the lowest PR whose files hold its cause, even when it was reported on a PR above; the report names both. A direct edit keeps its worktree; for a plan-backed PR, run `dev-worktree.sh create <issue>_<slug>-pr<N> <branch> origin/<branch>` and `link-deps <worktree>`. Delegate each PR's fix: for each finding about code behavior, a test that fails without the fix, then the fix, with the finding's evidence rerun and the local checks passing, committed on the PR's branch. A finding the chunk returns with options takes its recommendation under [Decisions](#decisions), recorded in the report, and goes back to the chunk. Rerun the checks here and confirm each new test fails without its fix.

Parents first, merge each changed branch, including one changed by a merge, into each PR branch whose PR base is that branch (`gh pr view <PR> --json baseRefName`), in that PR's worktree, created the same way; never rebase or force-push. Resolve a conflict here; one that needs a behavior choice goes to Decisions. Then rerun that branch's local checks; a failure goes to a review-fixes chunk on that branch and counts toward its `Failed fixes`. Every PR above a PR whose fix stopped is held: it gets no fix or merge, and its findings stay open. Push each changed branch with `git push origin <branch>`, and when a fix changes what a PR body describes, update it with `gh pr edit <PR> --body-file <file>`. There is no second `/code-review` round.

## 4. Finish

When every step the run includes completes, run `dev-worktree.sh remove` on each worktree the direct edit or step 3 created.

Any other outcome is a stop and ends the run with its worktrees kept: a stop under [Decisions](#decisions), a fix reaching the [CORE.md — Work](../../CORE.md#work) attempt limit, or run-stack ending with a plan not `published`. On a stop, write a [handoff](../handoff.md) recording the input, the options, the type and route with their reasons, the step that stopped, the root plan path or the direct edit's worktree, branch, and PR, the worktrees step 3 created, each PR's open blocking findings with their evidence, and any `Failed fixes: <n>/3`.

Report the type and route with their reasons, the issue, each draft PR's URL, and the `/code-review` findings with their fixes; include run-stack's report when it ran. List every decision taken for the user in one table for the user to audit, with columns Decision, Options, Why, and Plan: each `DD-*` whose Choice ends `by dev-autopilot`, from every plan in the stack, then each decision recorded only in the report. Then list what needs the user: each stop's reason, options, and recommendation, with any round such as `3/3` and any `Failed fixes: <n>/3`, and the handoff path. CI follows CORE.md — Work: cite known results or report it unverified.

## Decisions

On a question from triage, a subagent, or a review, or a stop under [plan.md — Changes](plan.md#changes), take the recommended option and record it as dev-autopilot's: in a DD as `Choice: <option>, by dev-autopilot` while the plan is unapproved ([plan.md — Changes](plan.md#changes)), otherwise in the report. This covers behavior, scope, contracts, the data model, dependencies, cost, and the PR split, including splitting, merging, inserting, or dropping plans under [plan.md — Stacks](plan.md#stacks). An approved plan follows plan.md — Changes; when the AC, TC, PC, or step of a plan whose approval is `auto-approved` cannot be met or followed as written, or it needs a contract from below, run `dev-stack.sh auto-reopen <plan>`, revise it under [Resume](#resume)'s revise rules with dev-autopilot's answers, and rerun step 2's run-stack. Stop for the user only when:

- a needs-changes verdict lands on a review's round limit, such as `3/3`, or fixes reach `Failed fixes: 3/3`;
- a bug does not reproduce, its mechanism stays unsupported, or its first fix option is containment or live-state remediation;
- the work would write to a shared environment outside Git;
- an input no source has is missing ([Handoffs](#handoffs));
- an approved plan's AC, TC, PC, or step cannot be met or followed as written, or it needs a contract from below, and `auto-reopen` refuses it.

## Resume

A resume is `/dev-autopilot <handoff path> <answers>`. It takes the options and state from the handoff and checks them against Git, `gh`, and, for a plan-backed run, `dev-stack.sh next <root>`; a mismatch is reported, and nothing starts. Otherwise it continues at the step that stopped, with the answers labeled as the user's:

- **Triage:** rerun step 1, skipping create-issue when the handoff has `#N`.
- **Plan-backed, before publication:** run-stack's revise step, under the rules below.
- **Direct edit:** continue at the step that stopped, reusing its worktree, branch, and any PR.
- **Step 3:** continue on the open findings, reusing the worktrees; a finding at `Failed fixes: 3/3` continues only when the answers grant more attempts.

Before publication, approved plans stay frozen under [plan.md — Changes](plan.md#changes). Run run-stack's revise step on the stopped plan and each plan above it that the answers change, where unapproved, with the stop's findings, the user's answers, and any of dev-autopilot's from [Decisions](#decisions) labeled as its own. A revision changes the spec, which ends an ordinary stop; a round limit or `Failed fixes: 3/3` holds until the user runs `dev-stack.sh resume <plan>`. Then run step 2's run-stack, which re-reviews, auto-approves, and publishes them, and continue with step 3. An answer that changes a plan the user approved, or one `auto-reopen` refused, comes with the user's `dev-stack.sh reopen <plan>`. A user's answer that changes no plan, such as more review rounds or fix attempts, comes with that `resume` and goes straight to run-stack.
