# /autopilot — Requirement to Reviewed PRs

Take one issue or requirement through triage, delivery, draft PRs marked ready, and one `/code-review` round. Pass the issue or requirement, then optionally `--until create-pr` to skip step 3, or, after a stop, its handoff path and the user's answers ([Resume](#resume)); any other option or value is reported before triage, and nothing starts. Invoking it authorizes the issues it creates, pushes without force, draft PRs, marking them ready in step 3, and `auto-approved` plans; never set `Status: approved`, which is the user's.

This session is the main agent: it locates edit points, routes, decides under [Decisions](#decisions) every question the stack's planner does not, and runs run-stack, create-issue, create-pr, and every worktree, push, PR, and merge-forward itself; subagents commit only where a step delegates it, and create only the scratch worktrees their own skills make. `Status:` changes stay with the phase that owns them under [plan.md — Sequence](plan.md#sequence). Every other step runs in a subagent built from its row in [Handoffs](#handoffs), fresh except that one dev-planner serves the stack's design-feature and every revise step after it, and reviewers are kept under [plan.md — Review](plan.md#review); where an agent is not installed, the general-purpose agent gets that agent's md file as its instructions and the same row. Without subagents, run each step here, one at a time, and say so.

## Handoffs

Each prompt names the agent's job, gives [CODING.md](../../CODING.md), the row's inputs, delegated and off-limits actions, and expected return, says others share the codebase, and carries any `Failed fixes: <n>/<limit>`; the subagent runs on the [skills README](../README.md) model and effort of the row's skill. A missing input is supplied before the subagent starts, never guessed; one no source has stops for the user. run-stack's phases take the inputs its step 2 and [plan.md — Review](plan.md#review) list.

## 1. Triage

1. **Input.** Read an issue (`#N` or URL) with `gh issue view`; anything else is the requirement as written.
2. **Bug or feature.** A bug is existing behavior that departs from expected, documented, or earlier behavior; anything else is a feature. For a request that reads either way, check the docs, tests, and Git history for the expected behavior: when they establish it and current behavior departs from it, the request is a bug; otherwise, including when the evidence conflicts, it is a feature. The evidence, or its absence, is the type's reason. An input holding an independent bug and an independent feature is split: triage and deliver the bug first, then the feature, each with its own issue; an input issue stays with the half it describes, or with the bug when it describes both, and create-issue makes the other's.
3. **Bug.** Run fix-bug. Stop if the bug does not reproduce, its mechanism stays unsupported, no fix option removes the root cause, or ongoing impact puts containment first under [fix-bug.md — Proposal](fix-bug.md#proposal); otherwise take the option [Decisions](#decisions) selects. When that option needs behavior no source establishes, the input is a feature from Locate on, and every input and Locate source this file gives for a bug still applies to it except `Type: fix`; design-feature picks the plan's Type.
4. **Locate.** Before routing, name every edit point as a file and symbol, or, for a file or symbol the change creates, its path confirmed absent: for a bug whose first fix option is taken, from fix-bug's Proposal; otherwise, the main agent reads the code under [explore.md](explore.md). For a code change, also name its test files: for a bug, the regression patch's; otherwise, the file its failing test goes in. A question reading cannot settle goes to [Decisions](#decisions).
5. **Route.** The first row that matches decides, for a bug and a feature alike, before any planning or coding; nothing later changes the route except the user's answer on resume.

   | Row | Condition | Route |
   |---|---|---|
   | 1 | The change needs a [design-system](design-system.md) document | stop under [Decisions](#decisions) |
   | 2 | The requested change itself needs a write to a shared environment outside Git | stop under [Decisions](#decisions) |
   | 3 | [plan.md — Scope](plan.md#scope) sends the change to the direct-edit path | direct edit |
   | 4 | The change is not contained under [plan.md — Scope](plan.md#scope) | plan-backed |
   | 5 | Otherwise | direct edit |

6. **Issue.** Without an input issue, run create-issue with the requirement, or for a bug with the problem, expected outcome, and diagnosis evidence, and in either case a `Triage` section giving the type with its reason, the route with the row that decided it, the edit points, and, for a bug, fix-bug's sibling defects the request does not cover and fix-bug's remediation as follow-ups; use its `#N` from here on. With an input issue, give that section in the report.

## 2. Deliver

**Plan-backed.** Run design-feature with the requirement, the issue, and for a bug `Type: fix` with the proposal and its regression patch. It decides its own questions under [Decisions](#decisions) and returns the stack; a question it returns is a stop under Decisions. Keep it for run-stack's revise steps. Run [run-stack](run-stack.md) `<root> --auto-approve`, which publishes the stack as draft PRs and cleans up once every plan is `reviewed`. When the planner returns a reshape, run its `renumber` or `drop` and resume it. For a change in the third column of the [plan.md — Changes](plan.md#changes) table on an approved plan, pass the choice to the planner, which revises an unapproved plan above it or writes a new plan ([plan.md — Stacks](plan.md#stacks)), then rerun run-stack. When run-stack ends with a plan stopped under [plan.md — Changes](plan.md#changes), apply [Decisions](#decisions), pass each choice, labeled as dev-autopilot's, to run-stack's revise step under [Resume](#resume)'s revise rules, and rerun run-stack; [Finish](#4-finish)'s stop applies only when Decisions stops.

**Direct edit.** On Base, the default branch unless the issue names one, create a worktree with [dev-worktree.sh](../../bin/dev-worktree.sh) `create <issue>_<slug> <branch> origin/<Base>`, the branch named by the project's convention, and run `link-deps <worktree>`. Delegate the change with the edit points and test files from triage's Locate step as its exclusive files, and commits on that branch. A code change starts with a failing test (for a bug, from the regression patch), shown failing and committed, then the change, shown passing; a docs or declarative config change, such as this dev flow's skills ([plan.md — Scope](plan.md#scope)), is the change alone. Either way, any original reproduction is rerun and the project's local checks and affected tests pass. When the chunk returns a change unfixed because it needs a file outside its exclusive files or, when Route row 5 decided it, is not contained, the main agent returns it to the chunk with a narrower change that fits its exclusive files and still meets the whole requirement, as a fix attempt; when no narrower change meets the whole requirement, it stops under [Decisions](#decisions). After the chunk returns a change within its exclusive files, the main agent runs any review the project's instructions require, reruns the checks, and, for a code change, confirms the test commit fails without the change; a failure returns to the chunk as a fix attempt. Then push with `git push -u origin <branch>` and open `gh pr create --draft --base <Base>` with a body under [create-pr.md](create-pr.md)'s rules.

## 3. Review the PRs

This step runs outside the plan-backed workflow: the plans are published, so no plan, `Status:`, or gate applies, and fixes follow the findings, not the spec. Review every PR before fixing any. For each PR, parents first, the main agent marks it ready with `gh pr ready <PR number>` when it is a draft; then run `/code-review <level> <PR number>` review-only, without `--fix` or `--comment`, where `<level>` is review-code's effort in the README; never `ultra`. Where `/code-review` is unavailable, the reviewer reviews `gh pr diff <PR number>` for correctness, security, and cost under CODING.md, with each finding's location and evidence. Correctness, security, and cost findings, a cost finding being unbounded or repeated work on a production path, block when they have a location and evidence, even when the review labels a cost finding a cleanup; cleanups and findings without a location or evidence are reported, not applied.

Then fix the blocking findings, parents first. Fix each finding on the lowest PR whose files hold its cause, even when it was reported on a PR above; the report names both. A direct edit keeps its worktree; for a plan-backed PR, run `dev-worktree.sh create <issue>_<slug>-pr<N> <branch> origin/<branch>` and `link-deps <worktree>`. Delegate each PR's fix: for each finding about code behavior, a test that fails without the fix, then the fix, with the finding's evidence rerun and the local checks and affected tests passing, committed on the PR's branch. A finding the chunk returns with options is decided under [Decisions](#decisions), recorded in the report, and goes back to the chunk. Rerun the checks here and confirm each new test fails without its fix.

Parents first, merge each changed branch, including one changed by a merge, into each PR branch whose PR base is that branch (`gh pr view <PR> --json baseRefName`), in that PR's worktree, created the same way; never rebase or force-push. Resolve a conflict here; one that needs a behavior choice goes to Decisions. Then rerun that branch's local checks and affected tests; a failure goes to a review-fixes chunk on that branch and counts toward its `Failed fixes`. Every PR above a PR whose fix stopped is held: it gets no fix or merge, and its findings stay open. Push each changed branch with `git push origin <branch>`, and when a fix changes what a PR body describes, update it with `gh pr edit <PR> --body-file <file>`. There is no second `/code-review` round.

## 4. Finish

When every step the run includes completes, run `dev-worktree.sh remove` on each worktree the direct edit or step 3 created that is still registered.

Any other outcome is a stop and ends the run with its worktrees kept: a stop under [Decisions](#decisions), fixes reaching their limit under [CORE.md — Work](../../CORE.md#work), a resume's failed `remove` or `git branch -m`, or run-stack ending with a plan not `published`. On a stop, write a [handoff](../handoff.md) recording the input, the options, the type and route with their reasons, the step that stopped; for a plan-backed run, the root plan path, or, before any plan is saved, the planner's open questions with their options; for a direct edit, its edit points and test files, worktree, branch, and PR; for a resume's failed `remove` or `git branch -m`, that step, whether `remove` succeeded, and the route as plan-backed by the user's answer; for a split input, the undelivered half; after a route switch on resume, any kept `<branch>-direct` branch and any draft PR the direct edit opened; the worktrees step 3 created, each PR's open blocking findings with their evidence, and any `Failed fixes: <n>/<limit>`.

Report each half's `Triage` section and issue, or, for an input not split, its `Triage` section and issue; after a route switch on resume, any kept `<branch>-direct` branch and any draft PR the direct edit opened; each PR's URL, draft or ready; and the `/code-review` findings with their fixes; include run-stack's report when it ran. List every decision taken for the user in one table for the user to audit, with columns Decision, Options, Why, and Plan: each `DD-*` whose Choice ends `by dev-autopilot`, from every plan in the stack, then each decision recorded only in the report. Then list what needs the user: each stop's reason, options, and recommendation, with any round such as `3/3` and any `Failed fixes: <n>/<limit>`, and the handoff path. CI follows CORE.md — Work: cite known results or report it unverified.

## Decisions

The stack's planner, or this session without subagents, applies this section to the questions its design-feature and revise steps raise; the main agent applies it to every other. On a question from triage, a subagent, or a review, or a stop under [plan.md — Changes](plan.md#changes), for a bug fix, take fix-bug's first fix option that includes every fix the user states as a constraint, and stop under "no option meets the whole requirement" when none does; for any other question, take the narrowest option that meets the whole requirement under [design-feature.md — Keep it simple](design-feature.md#4-keep-it-simple), and the recommended one among equally narrow options; a fix the requirement proposes follows [design-feature.md — Understand](design-feature.md#1-understand). Never drop or narrow what the requirement asks for. Report each wider option as a follow-up, and record the choice as dev-autopilot's: in a DD as `Choice: <option>, by dev-autopilot` while the plan is unapproved ([plan.md — Changes](plan.md#changes)), otherwise in the report. This covers behavior, scope, contracts, the data model, dependencies, cost, and the PR split, including splitting, merging, inserting, or dropping plans under [plan.md — Stacks](plan.md#stacks). An approved plan follows the [plan.md — Changes](plan.md#changes) table; after its `auto-reopen`, revise the plan under [Resume](#resume)'s revise rules and rerun step 2's run-stack. Stop for the user only when:

- a needs-changes verdict lands at or past a review's round limit, such as `3/3`, or fixes reach their limit, such as `Failed fixes: 3/3`;
- no option meets the whole requirement;
- the change needs a design-system document, whose approval is the user's;
- a bug does not reproduce, its mechanism stays unsupported, no fix option removes the root cause, or ongoing impact puts containment first;
- the requested change itself would write to a shared environment outside Git; a live operation that only remediates after the fix is a follow-up;
- an input no source has is missing ([Handoffs](#handoffs));
- an approved plan's AC, TC, PC, or step cannot be met or followed as written, or it needs a contract from below, and `auto-reopen` refuses it.

## Resume

A resume is `/dev-autopilot <handoff path> <answers>`. It takes the options and state from the handoff and checks them against Git, `gh`, and, for a plan-backed run with a saved root, `dev-stack.sh next <root>`; a mismatch is reported, and nothing starts. Otherwise it continues at the step that stopped, with the answers labeled as the user's:

- **Triage:** rerun step 1 on the stopped half of a split input, or on the input, skipping create-issue when the handoff has `#N`.
- **Split input:** after the stopped half completes, start the undelivered half at step 1.
- **Plan-backed, before any plan is saved:** resume design-feature, or rerun it with the answers when its planner is gone.
- **Plan-backed, before publication:** run-stack's revise step, under the rules below.
- **Direct edit:** continue at the step that stopped, reusing its worktree, branch, and any PR. An answer that chooses plan-backed instead switches the route in these steps, in order: (1) run `dev-worktree.sh remove` on the worktree; (2) when `remove` reports the branch kept, rename it to `<branch>-direct` with `git branch -m`, so no plan Branch reattaches it; (3) report any kept branch, any draft PR the direct edit opened, and the new route labeled as the user's answer, and record them for [Finish](#4-finish); (4) run step 2's plan-backed delivery, passing `<branch>` to design-feature as taken. A failed step (1) or (2) is a stop under [Finish](#4-finish); resuming it reruns the switch from the failed step.
- **Step 3:** continue on the open findings, reusing the worktrees; a finding whose fixes reached their limit continues only when the answers grant more attempts.

Before publication, approved plans stay frozen under [plan.md — Changes](plan.md#changes). Run run-stack's revise step on the stopped plan and each plan above it that the answers change, where unapproved, with the stop's findings, the user's answers, and the main agent's choices from [Decisions](#decisions) labeled as dev-autopilot's, stating that the planner decides the rest for the user under [Decisions](#decisions). A revision ends a stop only as [run-stack.md — Stops](run-stack.md#stops) says. Then run step 2's run-stack, which re-reviews, auto-approves, and publishes them, and continue with step 3. An answer that changes a plan the user approved, or one `auto-reopen` refused, comes with the user's `dev-stack.sh reopen <plan>`. A user's answer that changes no plan, such as more review rounds or fix attempts, comes with that `resume` and goes straight to run-stack.
